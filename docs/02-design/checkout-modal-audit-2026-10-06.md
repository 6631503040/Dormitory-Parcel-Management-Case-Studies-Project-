# Audit: หน้าต่างนำพัสดุออกตามห้อง

วันที่: 2026-10-06 · สาขา: `codex/frontend-ux-ui-refresh`

## Implementation Integrity Verdict

**ผ่านด้านความสอดคล้องของระบบ แต่ยังต้องปรับการใช้งาน** หน้าต่างใช้สี ฟอนต์ และสถานะร่วมกับหน้าเคาน์เตอร์ มีข้อมูลห้องและผู้รับจริงจากข้อมูลจำลอง มีการเลือกพัสดุและตรวจรหัสตรงห้อง ไม่มีเนื้อหาตกแต่งที่แสร้งเป็นความสามารถของผลิตภัณฑ์

ตัวตรวจ Impeccable ของ `Modals.jsx` และ `styles.css` คืน `[]` ไม่พบ deterministic findings ตามการตั้งค่าปัจจุบัน ผลนี้ไม่รับรอง UX หรือ WCAG และไม่ครอบคลุมปัญหาโฟกัส/การขยับที่พบระหว่างใช้งานจริง

## Executive Summary

คะแนน **15/20 — Good: ใช้งานได้ แต่ควรแก้จุดอ่อนก่อนส่งมอบ** เป็นคะแนนการตรวจเฉพาะหน้าต่างนี้ ไม่ใช่คะแนนทั้งระบบหรือการรับรอง WCAG

## วิธีตรวจและขอบเขต

- ตรวจภาพแนบซึ่งแสดงห้อง 203/1 มี 3 รายการ และอ่าน implementation ปัจจุบันที่ `docs/02-design/prototype/src/components/Modals.jsx` / `src/styles.css`.
- ตรวจหน้า localhost ผ่าน Codex in-app browser ที่ desktop 1280×720 และ mobile viewport 390×844. ข้อมูลใน browser มีห้อง 203/1 เพียง 1 record ต่างจากภาพแนบ จึงใช้ record นี้ทดสอบ state และไม่อ้างว่าทดสอบรายการ 3 ชิ้นจากภาพครบแล้ว
- ทดลองเลือก/ยกเลิกเลือก รหัสผิดห้อง เปิด/ยกเลิกยืนยันทั้งหมด และลำดับ Tab. ไม่ยืนยันการนำออก ไม่เขียนข้อมูลพัสดุ และไม่แก้ frontend/backend ในรอบ audit นี้
- `npm test`: 14/14 ผ่าน เป็นการทดสอบกฎข้อมูล ไม่ใช่การทดสอบ UX หรือ screen reader. Production build ผ่าน
- ไม่ได้ทดสอบเครื่องสแกนจริง screen reader อุปกรณ์สัมผัสจริง text zoom หรือ load test. Mobile viewport เป็นหลักฐาน layout ไม่ใช่ touch gesture test

## Detailed Findings

### [P1] โฟกัสหลุดเมื่อเข้าขั้นยืนยันทั้งหมด

- **ตำแหน่ง:** `Modals.jsx:182–187`.
- **หมวด:** Accessibility.
- **หลักฐาน:** กด Enter ที่ “นำออกทั้งหมดของห้อง (1)” แล้ว `document.activeElement` กลายเป็น `BODY` เพราะปุ่มถูกถอดออก. Tab ถัดไปไป “ปิดหน้าต่าง” แทนปุ่มในขั้นยืนยัน. กดยกเลิกแล้วโฟกัสหลุดอีกครั้ง
- **ผลกระทบ:** ผู้ใช้คีย์บอร์ดต้องเดินผ่าน control เดิมเพื่อกลับมายืนยัน; ผู้ใช้เทคโนโลยีช่วยเหลืออาจเสียบริบทของขั้นตอน
- **มาตรฐาน:** เกี่ยวข้องกับ WCAG 2.4.3 Focus Order; ไม่ใช่หลักฐานว่า native dialog ไม่มี focus containment
- **ข้อเสนอ:** เมื่อเปิด confirmation ย้ายโฟกัสไป “ยกเลิก” ซึ่งปลอดภัยกว่า และเมื่อยกเลิกคืนไปปุ่มเปิด confirmation หลัง render กลับมา. จัดข้อความยืนยันให้สัมพันธ์กับกลุ่มปุ่ม
- **คำสั่ง:** `$impeccable harden`.

### [P2] ไม่เห็นสถานะ “ยังไม่เลือก” ทำให้แถวดูเหมือนข้อมูลเฉย ๆ

- **ตำแหน่ง:** `Modals.jsx:175–177`; `styles.css:157`.
- **หมวด:** Implementation Integrity / UX affordance.
- **หลักฐาน:** ไอคอน Check ถูกซ่อนด้วย `visibility: hidden` เมื่อยังไม่เลือก; ในภาพแนบจึงเหลือเพียงกรอบและเลขพัสดุ ไม่มี checkbox ว่าง
- **ผลกระทบ:** พนักงานใหม่ต้องเดาว่ากดทั้งแถวเพื่อเลือกได้ ขณะที่ปุ่มนำออกถูก disabled และช่องสแกนเด่นกว่า
- **มาตรฐาน:** ไม่อ้างเป็น WCAG violation เพราะปัจจุบันใช้ native button กับ `aria-pressed` และมี accessible name
- **ข้อเสนอ:** แสดง checkbox ว่างเสมอ กดได้ทั้งแถว และแสดง check เมื่อเลือก. ถ้าเปลี่ยนเป็น checkbox ให้ใช้ semantic และ keyboard behavior ของ checkbox ให้ครบ. เพิ่ม “เลือกทั้งหมด” ใกล้หัวรายการ แล้วใช้ปุ่มยืนยันหลักเพียงจุดเดียว; รักษาขั้นยืนยัน bulk action ตามความจำเป็น
- **คำสั่ง:** `$impeccable clarify`.

### [P2] ข้อผิดพลาดของรหัสอยู่ท้ายหน้าต่างและไม่ผูกกับช่องกรอก

- **ตำแหน่ง:** `Modals.jsx:170,192` เทียบกับ `LabeledInput:39–48`.
- **หมวด:** Accessibility / Form feedback.
- **หลักฐาน:** กรอก `TH8827301923` ขณะเลือกห้อง 203/1 ได้ข้อความผิดห้องท้ายหน้าต่างหลัง “วิธีใช้งาน”. Input ยัง `aria-invalid="false"` และ `aria-describedby` อ้างเฉพาะคำแนะนำ Enter เพราะไม่ได้ส่ง `error` เข้า `LabeledInput`
- **ผลกระทบ:** ผู้ใช้ต้องมองไกลจากจุดทำงานเพื่อหาสาเหตุ โดยเฉพาะเมื่อ dialog ยาวหรือเลื่อนอยู่; การกลับมาที่ช่องไม่เชื่อมโยงกับ error
- **มาตรฐาน:** เกี่ยวข้องกับ WCAG 1.3.1 และ 3.3.1; ข้อความเดิมมี `role="alert"` จึงไม่รายงานผิดว่าไม่มีการประกาศ error เลย
- **ข้อเสนอ:** แยก scan error ออกจาก save error; แสดง scan error ใต้ช่องเลขพัสดุและเชื่อมด้วย `aria-describedby` / `aria-invalid`. เก็บ save error ใกล้ปุ่มยืนยัน
- **คำสั่ง:** `$impeccable harden`.

### [P2] หน้าต่างขยับเมื่อเลือกพัสดุครบทั้งหมด

- **ตำแหน่ง:** `Modals.jsx:187`; `styles.css:145,225`.
- **หมวด:** Responsive Design / Layout stability.
- **หลักฐาน:** เมื่อเลือกครบ ปุ่ม “นำออกทั้งหมดของห้อง” ถูกถอดออก. ที่ desktop ห้องที่มี 1 record ความสูง dialog ลดจาก 557.38 เป็น 503.38 px; top เปลี่ยนจาก 81.31 เป็น 108.31 px และช่องกรอกขยับลง 27 px. ค่ามาจาก before/after ของสถานะเดียวกันโดยไม่มี feedback
- **ผลกระทบ:** จุดที่กำลังอ่านและกดเคลื่อนระหว่างงานซ้ำ ๆ ตรงกับความกังวลเรื่องกล่องขยาย/หดที่ผู้ใช้แจ้งก่อนหน้า
- **มาตรฐาน:** ไม่มีการอ้าง WCAG violation หรือค่า CLS จากการทดสอบนี้
- **ข้อเสนอ:** รักษาความสูงของ footer การยืนยันให้คงที่ หรือใช้ “เลือกทั้งหมด” เป็น control คงที่ในหัวรายการ และปุ่มนำออกหลักคงตำแหน่ง
- **คำสั่ง:** `$impeccable layout`.

### [P2] รายการยาวยังต้องเลื่อนภายในหน้าต่างก่อนเปลี่ยนหน้า

- **ตำแหน่ง:** `Modals.jsx:129,175,180`; `styles.css:145,221`.
- **หมวด:** Responsive Design.
- **หลักฐานจากโค้ด:** 25 records ต่อหน้า แต่ list สูงได้เพียง 240 px พร้อม `overflow-y:auto`; dialog เองก็เลื่อนได้. แถวปกติที่วัดสูง 46.80 px ยังไม่รวม gap8 จึงเห็นพร้อมกันประมาณ 4–5 แถว. ปุ่ม pagination อยู่นอก list
- **ผลกระทบ:** หน้าเดียวมีทั้งการเลื่อน list และการเปลี่ยนหน้า; ในจอเตี้ยหรือรายการมีหมายเหตุยาวจะมีการเลื่อน dialog เพิ่ม ทำให้ตรวจว่าชิ้นใดเลือกแล้วได้ยาก
- **มาตรฐาน:** ไม่รายงานว่ามี keyboard trap; ปริมาณ 25 records ไม่ได้ถูกจำลองใน browser รอบนี้
- **ข้อเสนอ:** กำหนดจำนวนรายการต่อหน้าให้เข้ากับพื้นที่ที่เห็นจริงและความต้องการผู้ใช้ เช่น 8 เป็นจุดเริ่มต้น ตรวจ mobile เพิ่มเพื่อหลีกเลี่ยงเลื่อนซ้อน. ปุ่มเปลี่ยนหน้าและปุ่มยืนยันควรอยู่ในตำแหน่งคงที่ พร้อมจำนวนที่เลือกข้ามหน้า
- **คำสั่ง:** `$impeccable adapt`.

### [P3] สีพื้น selected ถูก hover ทับ

- **ตำแหน่ง:** `styles.css:158,223`.
- **หมวด:** Theming / Implementation Integrity.
- **หลักฐานจาก CSS:** `.selection-row:hover { background: var(--desk-bg) !important; }` มี priority เหนือพื้นสี selected ที่ใช้ `--desk-primary-light` แม้ aria-pressed ยัง true
- **ผลกระทบ:** ขณะชี้เมาส์ สีที่ช่วยยืนยันการเลือกจางหาย; check และขอบน้ำเงินยังอยู่ จึงไม่ได้สูญเสียสถานะทั้งหมด
- **มาตรฐาน:** ไม่อ้าง WCAG 1.4.1 เพราะมี check และ semantic state อยู่แล้ว. ประเด็นนี้ยืนยันจาก cascade ไม่ใช่ screenshot hover ที่ tool จับไม่ได้
- **ข้อเสนอ:** ให้ selected:hover คงพื้น selected และยกเลิก `!important` ที่ทับ state
- **คำสั่ง:** `$impeccable polish`.

## Patterns & Positive Findings

รูปแบบปัญหาหลักคือ control ถูกถอด/เพิ่มตาม state แต่ยังไม่ได้จัดการโฟกัสและพื้นที่รองรับให้ครบ; พบทั้ง confirmation และ footer เมื่อเลือกครบ. อีกจุดคือ error ที่มีโครงสร้างรองรับใน shared input แต่ checkout ไม่ได้ส่งข้อมูลเข้าไปใช้

สิ่งที่ควรรักษา:

- ห้องและผู้รับอยู่ด้านบน เห็นบริบทก่อนนำออก; เปลี่ยนห้องที่มีรายการเลือกไว้ต้องยืนยัน
- ปุ่มหลัก disabled เมื่อยังไม่เลือก และนับจำนวนที่เลือก; selected มี check และสี ไม่ใช้สีอย่างเดียว
- Native dialog มีชื่อจาก heading พร้อม Escape และคืนโฟกัสเมื่อปิด
- กฎข้อมูลตรวจรหัสเต็ม รหัสผิดห้อง พัสดุที่นำออกแล้ว รายการซ้ำ และข้อมูลเก่าก่อนบันทึก; มี tests รองรับ
- การยืนยัน bulk ระบุจำนวนและเลขห้อง; ไม่ทำรายการทันทีจากลิงก์
- ปุ่มที่วัดใน mobile ≥44×44 px; ช่องรหัส 16 px; มี focus indicator และ reduced-motion ลด transition ของ control
- Contrast เทียบพื้นขาว: text **16.10:1**, muted **5.90:1**, primary **6.85:1**, warning **6.57:1** ผ่าน AA สำหรับข้อความปกติที่ตรวจ. Border **1.29:1**; ไม่ฟันธงเป็น failure เพราะขอบการ์ดไม่ใช่เพียงสัญญาณเดียวที่ใช้ระบุข้อความ/สถานะ
- คำแนะนำรายละเอียดเก็บไว้ใน “วิธีใช้งาน” ลดข้อความซ้ำในงานประจำ

## Recommended Actions

1. **[P1/P2] `$impeccable harden`** — จัดโฟกัส confirmation/คืนโฟกัส และผูก scan error กับช่องกรอก
2. **[P2] `$impeccable clarify`** — ทำให้การเลือกมองเห็นได้ทันทีด้วย checkbox และจัด “เลือกทั้งหมด” ใกล้รายการ
3. **[P2] `$impeccable layout`** — รักษาพื้นที่ footer ให้คงที่ ป้องกันหน้าต่างขยับเมื่อเลือกครบ
4. **[P2] `$impeccable adapt`** — วางรายการและ pagination ให้เข้ากับ desktop/mobile โดยลด scroll ซ้อน
5. **[P3] `$impeccable polish`** — แก้ selected:hover และตรวจสถานะ unselected / partial / all / error / confirmation ในรอบจบ

สามารถสั่งทำทีละรายการ ทั้งหมด หรือเรียงลำดับใหม่ได้ แล้วรัน `$impeccable audit` อีกครั้งหลังแก้เพื่อเทียบคะแนนและหลักฐาน

คะแนน 15/20 ด้านบนเป็นผล audit ก่อนแก้ ไม่ได้เปลี่ยนคะแนนย้อนหลังหรืออ้างการรับรอง accessibility. การตรวจหลังแก้เป็น functional/layout confirmation ด้วยข้อมูลจำลอง; รายการยาวผิดปกติและจอเตี้ยมากยังใช้พื้นที่เลื่อนเนื้อหาเดียว โดยปุ่มยืนยันอยู่ใน footer. ไม่แก้ backend และไม่บันทึกข้อมูลพัสดุจริง.
